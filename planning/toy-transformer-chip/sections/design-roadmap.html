Design Roadmap

The completed path from prerequisite math through a prechecked 2x2 layout.

Roadmap Overview

We followed the roadmap top-down: study the math, freeze an exact Python model, size the architecture, implement RTL, compare it with the model, then harden and precheck the design.

Phase Purpose Planning Output Status
0. Prerequisite study Understand the minimum math story before writing models. Notes on matmul, dot products, simple single-head self-attention, and softmax. Complete
1. Python/Numpy model Define the exact toy computation and expected results. Golden model, data format rules, examples, expected byte streams. Complete
2. High-level chip architecture Choose the hardware shape before writing RTL. Fixed architecture brief, memory/register sizing, MAC count, FSM sketch, host/chip split, IO protocol. Complete
3. RTL design Describe the selected architecture as hardware modules and signals. Module boundaries, signal contract, state machine, reset behavior. Complete
4. RTL simulation Check the Verilog behavior against the Python model before tapeout work. cocotb test plan, waveform checklist, pass/fail criteria. Complete
5. Tiny Tapeout template / hardening Package the design for the ASIC flow and verify the hardened netlist. Tiny Tapeout wrapper plan, hardening checklist, gate-level simulation plan. Local flow complete

Design Sequencing

The implemented design went directly to fixed-shape attention after validating the MAC primitive. It reuses the same ready/valid byte boundary and two MAC lanes across every phase.

  • The standalone PE remains as the smallest arithmetic test.
  • FLUSH invalidates the current transaction and all load flags.
  • The Python model defines every projection, attention, normalization, and byte-level result.
  • Source RTL and the powered gate netlist now pass the same complete host transaction.

Phase 0: Prerequisite Study

Before choosing a model or hardware primitive, study the smallest version of the math. The target is one simple single-head self-attention path, not full transformer coverage.

Deliverables Success Criteria Decisions Made Here

Short notes for one-head self-attention: Q, K, V, score, softmax, weighted V. We can trace one tiny example by hand with sequence length 4. Chosen for now: the chip should compute Q/K/V projections rather than only consuming precomputed Q/K/V.

Phase 1: Python/Numpy Model

This is the source of truth for behavior. It should be small enough to understand in one sitting and strict enough that the RTL has no ambiguity.

Deliverables Success Criteria Decisions Made Here

Softmax approximation candidates expressed in Python. At least one approximation is simple enough to explain and compare against exact softmax. Whether softmax is host-assisted, LUT-like, argmax-like, or simple normalization.
Problem-size candidates such as sequence length, hidden size, and tile shape. Examples are small enough to fit the Tiny Tapeout mindset and large enough to tell the transformer story. Whether int4 gives enough room to justify using it over int8.

Accumulator Width Rationale

Use a signed 16-bit accumulator as the first working choice. Signed int4 values have range [-8, 7]. One product can reach 64, and a 2-wide dot product can reach 128, which already does not fit cleanly in signed 8-bit. A 9- or 10-bit accumulator could work for the smallest case, but 16-bit is easier to explain, easier to serialize over an 8-bit output bus, and gives room for 4-wide toy dots later.

  • Internal dot-product accumulator: signed 16-bit.
  • Q/K/V projection outputs: clamp or requantize back to int4 before the next stage.
  • Boundary outputs for debugging: expose 16-bit signed values as high byte then low byte.
  • Reason to avoid narrower accumulators for now: they save bits but complicate edge cases and explanation.

Softmax Approximation Hardware Options

Exact softmax is not a good tiny-chip target because it needs exponentials and division. A softmax approximation can be realized in hardware if we choose one that maps to small comparators, shifts, adders, or tiny lookup tables.

Option Hardware Shape Planning Status
Clipped-linear attention Subtract row max, add B = 4, clamp negatives to zero, sum weighted V, then normalize by sum_u. Working choice, with Q0.8 reciprocal LUT normalization and round-to-nearest.
Hardmax attention Find max score and select that token's V vector with one-hot weights. Fallback if clipped-linear normalization is too costly.
Host-assisted softmax Chip emits scores; host computes weights; chip optionally consumes weights to compute weighted V. Fallback if any on-chip approximation becomes too distracting.

Normalization LUT Rationale

A lookup table is reasonable for the clipped-linear normalization because the denominator range is tiny. If the sequence length is 4 and B = 4, each clipped weight u_i is in [0, 4], and the max-scoring token always contributes 4. That means sum_u is only in [4, 16].

  • Store fixed-point reciprocals for denominators 4 through 16.
  • Compute numerator = sum(u_i * V_i) with the 16-bit accumulator path.
  • Approximate numerator / sum_u as (numerator * reciprocal[sum_u]) >> scale_bits.
  • If the LUT multiply is still too much, fall back to hardmax attention or host-assisted normalization.

Locked Phase 2 Inputs

  1. Use sequence length 4, embedding width 2, one head, and Q/K/V width 2.
  2. Use signed int4 two's-complement range [-8, 7], two packed values per byte.
  3. Keep Q/K/V projection on-chip using integer input embeddings and integer Wq, Wk, Wv matrices.
  4. Use clipped-linear attention with B = 4, Q0.8 reciprocal LUT normalization, round-to-nearest, and saturating int4 clamp.
  5. Decide clamp/requantization points from 16-bit accumulators back to int4 between stages.
  6. Generate reference traces for Q, K, V, scores, clipped-linear weights, final output, and byte streams.
  7. Use the High-Level Chip Architecture page as the Phase 2 sizing brief.

Phase 2: High-Level Chip Architecture

This is where we plan memory size, registers, MAC count, control states, host/chip split, and the external protocol. It happens before detailed RTL design. The current fixed scope lives in the High-Level Chip Architecture page.

Deliverables Success Criteria Decisions Made Here
Block diagram and datapath sketch. Someone can explain how bytes become outputs without reading RTL. Chosen primitive: two reusable MAC lanes; scores serialize through lane 0.
Resource sketch for MAC units, accumulators, registers, and any tiny buffers. The design has a plausible Tiny Tapeout fit before implementation begins. Number of MAC units, accumulator width, memory/register budget, and reuse strategy.
Host/chip protocol sketch with command, load, compute, drain, and flush behavior. The protocol can run matmul/dot-product first and leave room for attention later. Which state lives on-chip versus in the Python host/demo script.

Phase 3: RTL Design

This phase turned the selected architecture into the implemented Verilog module and signal contracts.

Deliverables Success Criteria Decisions Made Here
Module list with inputs, outputs, registers, and reset behavior. Each module has one job and a clear test strategy. Exact module boundaries and signal names.
FSM state table for command/load/compute/drain/flush. Every transition has an input condition and expected output behavior. Whether the design uses a single controller or split protocol/datapath controllers.
Cycle-level output ordering and valid/done behavior. The RTL contract can be tested against the Python byte traces. Exact handshake semantics and what happens on reset or interrupted jobs.

Phase 4: RTL Simulation

This phase proves that the RTL matches the Python model. The first simulator target should be cocotb plus Icarus Verilog, because the tests can reuse Python expected outputs.

Deliverables Success Criteria Decisions Made Here
cocotb test plan driven by the same byte protocol as the future board demo. RTL outputs match the Python model for representative examples. Which tests are required before hardening is allowed.
Waveform checklist for reset, load, compute, drain, flush, valid, and accumulators. Waveforms make the pipeline understandable as an educational artifact. Which internal signals should be inspected or exposed during debug.
Failure-case tests for reset during operation and bad/partial input streams. The design recovers to a known state without ambiguous outputs. How defensive the protocol should be for a toy chip.

Phase 5: Tiny Tapeout Template / Hardening

This phase packaged the stable RTL into the Tiny Tapeout wrapper, ran hardening, checked the powered gate-level behavior, created the submission bundle, and passed local precheck.

Deliverables Success Criteria Decisions Made Here
Tiny Tapeout wrapper mapping for `ui_in`, `uo_out`, `uio_in`, `uio_out`, `uio_oe`, `clk`, and `rst_n`. The wrapper preserves the simulated byte protocol. Final pin assignment and any debug/status bits.
Hardening checklist and gate-level simulation plan. Docs, GDS, and gate-level simulation pass on the same golden-model examples. Whether the current design is ready to submit or should be simplified.
Submission-readiness notes. The project has a clear demo story, tests, and known limitations. Which shuttle/template path to target.
